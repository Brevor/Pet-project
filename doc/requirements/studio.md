## 1. Назначение и границы

Модуль описывает ядро студии как рабочего пространства: создание студии, учётные записи и
персонал, роли и права, залы, каталог курсов и расписание.

Запрос пользователя: «создание студии, заведение персонала с необходимыми ролями (владелец,
администратор, куратор, преподаватель, ассистент, ученик), создание списка занятий,
создание доступных залов для тренировок, возможность создавать расписание занятий».

### 1.1. Термины

| Термин | Значение в этом документе |
|---|---|
| **Студия** | Организация-арендатор (tenant). Одна инсталляция обслуживает несколько студий |
| **Аккаунт** | Учётная запись пользователя. Существует независимо от студии |
| **Членство** | Связь аккаунта и студии. Хранит набор ролей участника в этой студии |
| **Сотрудник** | Участник с хотя бы одной ролью из: владелец, администратор, куратор, преподаватель, ассистент |
| **Ученик** | Участник с ролью «ученик» |
| **ИТ-администратор системы** | Служебная роль уровня инсталляции: создаёт аккаунты через API/БД, вне UI студии |
| **Зал** | Физическое помещение для тренировок (название, вместимость) |
| **Курс** | Единица каталога — то, что в запросе названо «занятием»: название, направление, уровень, тип, длительность, вместимость |
| **Сеанс** | Курс, поставленный в расписание на конкретные дату/время, зал и преподавателя |
| **Расписание** | Набор сеансов студии, отображаемый по дням и неделям |

Разделение «курс — сеанс» принципиально: правки каталога не переписывают прошлые сеансы (`Q4`).

## 3. Учётные записи и персонал

Приглашений нет: **аккаунт** создаётся самостоятельной регистрацией или ИТ-администратором системы,
а **членство в студии** оформляет владелец или администратор, указывая email существующего аккаунта.
Аккаунт глобальный и не содержит `studio_id`; `studio_id` есть у членства и у остальных сущностей модуля.

| ID | Требование | Приоритет | Приёмка (Given → When → Then) | Источник |
|---|---|---|---|---|
| ACC-1 | Самостоятельная регистрация аккаунта: email + пароль; аккаунт не привязан к студии | Must | Given новый email, When регистрируется, Then аккаунт создан, доступен экран «создать студию / присоединиться» | запрос, proposal §3 |
| ACC-2 | ИТ-администратор системы может создать аккаунт через служебный API или напрямую в БД | Must | Given ИТ-администратор, When создаёт аккаунт, Then пользователь может войти; в интерфейсе студии такого сценария нет | запрос |
| ACC-3 | Вход по email и паролю, выдача JWT | Must | Given верные учётные данные, When вход, Then выдан токен; при неверных — 401 без раскрытия, что именно неверно | proposal §3, §6 |
| ACC-4 | Аккаунт без членства в студии видит только экран создания студии или присоединения | Must | Given аккаунт без членств, When открывает приложение, Then разделы студии недоступны | запрос |
| STF-1 | Владелец или администратор добавляет в студию существующий аккаунт по email, назначая одну или несколько ролей | Must | Given зарегистрированный email, When администратор добавляет его с ролью «преподаватель», Then создано членство; письма не отправляются | запрос |
| STF-2 | Если аккаунт с таким email не зарегистрирован — понятная ошибка | Must | Given незарегистрированный email, When администратор добавляет его, Then ответ 404 «пользователь не зарегистрирован» с подсказкой, что делать | запрос |
| STF-3 | Повторное добавление того же аккаунта в студию отклоняется | Must | Given участник уже в студии, When администратор добавляет тот же email, Then ответ 409, дубль членства не создан | предложение |
| STF-4 | Набор ролей участника можно менять; ролей может быть несколько | Must | Given участник с ролью «ассистент», When администратор добавляет роль «преподаватель», Then у него обе роли, права объединены (ROL-2) | ответ Q2 |
| STF-5 | Передача владения студией | Must | Given владелец, When передаёт владение участнику, Then новый владелец получает роль «владелец», прежний — «администратор»; владелец в студии ровно один | A5 |
| STF-6 | Исключение участника из студии или деактивация членства без удаления аккаунта и истории | Must | Given исключённый участник, When пытается открыть студию, Then доступ запрещён; его прошлые сеансы сохраняются | A5 |
| STF-7 | Запрет исключения последнего владельца | Must | Given владелец единственный, When пытается исключить себя, Then ответ 409 с предложением передать владение | предложение |
| STF-8 | Список персонала с фильтром по роли и поиском по имени и email | Must | Given 12 сотрудников, When выбран фильтр «куратор», Then в списке только участники с этой ролью | запрос |
| STF-9 | Ученика добавляет администратор: при отсутствии аккаунта он создаётся, ученик получает письмо для установки пароля | Must | Given новый email ученика, When администратор добавляет его, Then аккаунт и членство с ролью «ученик» созданы, ученик может войти после установки пароля | ответ Q6 |
| STF-10 | Ученик может зарегистрироваться самостоятельно и присоединиться к студии | Must | Given самостоятельная регистрация, When ученик присоединяется к студии, Then создано членство с ролью «ученик», других ролей нет | ответ Q6, Q7 |

## 4. Роли и права

Набор ролей: **владелец, администратор, куратор, преподаватель, ассистент, ученик** (`Q2`).
Сотрудник может иметь несколько ролей; права складываются.

| ID | Требование | Приоритет | Приёмка (Given → When → Then) | Источник |
|---|---|---|---|---|
| ROL-1 | Роль — значение из фиксированного набора; у участника хранится набор ролей (не менее одной) | Must | Given добавляется участник без ролей, When сохраняется, Then ответ 422 | запрос |
| ROL-2 | При нескольких ролях права — объединение; ограничение одной роли не может отменить право, данное другой | Must | Given участник с ролями «преподаватель» и «куратор», When создаёт сеанс, Then действие разрешено правом куратора | ответ Q2 |
| ROL-3 | Права определяются матрицей 4.1 | Must | Given роль «ассистент», When вызывается изменение зала, Then ответ 403 | запрос |
| ROL-4 | Права проверяются на API; интерфейс лишь скрывает недоступные действия | Must | Given прямой запрос в обход UI, When у участника нет права, Then ответ 403, изменение не применено | proposal §7 п.5 |
| ROL-5 | Владелец имеет полный доступ, включая архивирование студии | Must | Given владелец, When выполняет любое действие модуля, Then разрешено | A5 |
| ROL-6 | Администратор имеет полный доступ, кроме управления владельцем и архивирования студии | Must | Given администратор, When меняет роль владельца, Then ответ 403 | A5 |
| ROL-7 | Куратор управляет залами, курсами, расписанием и учениками; персонал и настройки студии недоступны | Must | Given куратор, When создаёт сеанс, Then успех; при попытке добавить сотрудника → 403 | ответ Q2 |
| ROL-8 | Преподаватель видит общее расписание студии (только просмотр) и не редактирует его | Must | Given преподаватель, When открывает расписание, Then видит все сеансы; кнопок создания и правки нет, прямой запрос → 403 | ответ: общий просмотр |
| ROL-9 | Ассистент видит общее расписание студии (только просмотр) | Must | Given ассистент, When открывает расписание, Then видит все сеансы, редактирование недоступно | ответ: общий просмотр |
| ROL-10 | Ученик видит общее расписание студии (только просмотр) и свой кабинет | Must | Given ученик, When открывает расписание, Then видит все сеансы студии без права правки | ответ: общий просмотр |

## 8. Нефункциональные требования модуля

| ID | Требование | Приёмка |
|---|---|---|
| NFR-1 | Изоляция по `studio_id` проверяется автоматическим тестом | Тест: пользователь A не получает объект B ни в одном эндпоинте модуля |
| NFR-2 | Проверка прав — на сервере, для каждого эндпоинта; при нескольких ролях учитывается объединение прав | Тест: запрос без права → 403, данные не изменены |
| NFR-3 | Время хранится в UTC, отображается в часовом поясе студии | Тест: сеанс 18:00 в зоне +03:00 отображается как 18:00 после смены часового пояса браузера |
| NFR-4 | Валидация входных данных: обязательные поля, диапазоны, уникальность — с кодами 422/409 | Тест: пустое название зала → 422, дубль → 409 |

| **Q8** | Нужна ли роль «родитель» (оплачивает, видит прогресс ребёнка)? | **открыт** (из proposal §5) | В матрицу 4.1 не входит; при добавлении меняет права на кабинет ученика |

Закрытые ответами 2026-11-22: Q1 (SaaS, самостоятельная регистрация владельца), Q2 (шесть ролей,
матрица 4.1 подтверждена), Q4 (каталог курсов), Q5 (расширение Current Phase), Q6 (ученик —
администратором или самостоятельно).

## 10. Что не входит в модуль

- Абонементы, оплаты, задолженности (A3, A4) — отдельные модули.
- Отметка посещаемости и QR-отметка (A2, A6.5).
- Программа лояльности (Known Unknown, proposal §4).
- Уведомления, кроме письма для установки пароля (proposal §4).
- Онлайн-оплата, мобильное приложение, публичный API (proposal §4).
- Группы и запись учеников в группы — соседний модуль.

## 12. Критерий готовности модуля (сквозной сценарий)

1. Владелец регистрируется сам, создаёт студию и задаёт рабочие часы (SaaS).
2. Куратор, преподаватель и ассистент регистрируются самостоятельно; владелец добавляет их в
   студию по email с нужными ролями. Писем-приглашений нет.
3. Одному сотруднику владелец назначает две роли (например, «преподаватель» и «куратор») —
   права объединяются.
4. Куратор создаёт два зала и три курса в каталоге.
5. Куратор ставит повторяющийся сеанс по Пн и Ср и разовый на субботу.
6. Попытка поставить два сеанса в один зал в одно время — отклонена с указанием конфликта.
7. Преподаватель, ассистент и ученик видят общее расписание студии в режиме просмотра;
   правка им недоступна.
8. Ученик добавлен администратором (или зарегистрировался сам) и видит только свой кабинет.
9. Пользователь другой студии не получает ни одного объекта этих данных (проверяется тестом).
