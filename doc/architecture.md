## 1. Вердикт анализа

Требования v0.4.0 **укладываются** в архитектуру v1.0.0: новых сущностей нет, все сценарии
используют существующие таблицы и модули. Нужны пять точечных изменений:

| # | Изменение | Затрагивает | Требования |
|---|---|---|---|
| 1 | поле `courses.teacher_membership_id` (миграция 006) | `courses`, `memberships` | CLS-7 |
| 2 | длительность сеанса — только из курса; `durationMin` убран из API планирования | `schedule` | CLS-8, SCH-1, SCH-2, SCH-10 |
| 3 | уточнение прав: `members.read` — только owner/admin; справочник преподавателей и список учеников вынесены отдельно | `rbac`, `members`, `schedule` | ROL-7, ROL-12 |
| 4 | запрет менять собственный набор ролей через `PATCH /members` | `members` | ACC-9 |
| 5 | спецификация видимости UI (схему не меняет) | клиент | ROL-11, ROL-12, STF-11, ROM-7 |

**Decision Gate по схеме закрыт 2026-11-22** (`HANDOFF.md` §4): добавление
`courses.teacher_membership_id` разрешено, таблица заявок преподавателей не нужна (Q9 закрыт).
Других изменений схемы в v0.4.0 нет: `durationMin` остаётся колонкой `class_series`, но перестаёт
быть входным параметром API.

Историческая справка: v1.0.0 фиксировала первую версию архитектуры до реализации. К 2026-11-22
реализованы M0–M7 (46 тестов), поэтому ниже описанное совпадает с кодом, кроме изменений 1–5.
Отдельно при сверке контракта с кодом найдено расхождение: `GET /schedule` отдаёт `id` вместо
`sessionId` — правится вместе с изменением 2 (см. `doc/contracts.md` §7).

## 2. Границы

Входит (Фаза 1, расширена 2026-11-22): аутентификация, студия и рабочие часы, участники и роли,
залы, каталог курсов, расписание сеансов, видимость интерфейса по правам.

Не входит: посещаемость, абонементы, личный кабинет ученика, уведомления, программа лояльности.
Эти модули не влияют на модель данных ниже — точки расширения появляются вместе с ними.

## 3. Топология

```
┌──────────────────────────┐        HTTPS/JSON         ┌──────────────────────────┐
│  Клиент: React + Vite    │  Authorization: Bearer    │  API: Node.js + Fastify  │
│  Tailwind, SPA           │ ────────────────────────► │  REST /api/v1            │
│  (студия, персонал,      │ ◄──────────────────────── │  JWT, RBAC, tenant guard │
│   залы, курсы, расписание)│         ошибки 4xx         └───────────┬──────────────┘
└──────────────────────────┘                                       │ SQL
                                                          ┌────────▼─────────┐
                                                          │   PostgreSQL     │
                                                          │  + btree_gist    │
                                                          └──────────────────┘
```

Один инстанс API и БД, без Kubernetes (`proposal.md` §6). Клиент — SPA, серверного рендеринга нет.

## 5. Модель данных

Все таблицы, кроме `users`, содержат `studio_id NOT NULL` с индексом (STU-5).
Ссылочная целостность между сущностями студии — составными внешними ключами
`(studio_id, <id>) → parent(studio_id, id)`, чтобы объект одной студии нельзя было привязать к другой.

### 5.1. `users` — глобальный аккаунт (без `studio_id`)

| Поле | Тип | Ограничения |
|---|---|---|
| id | uuid | PK |
| email | text | NOT NULL, UNIQUE по `lower(email)` |
| password_hash | text | NOT NULL (argon2id) |
| display_name | text | NULL |
| is_active | bool | NOT NULL DEFAULT true |
| created_at | timestamptz | NOT NULL DEFAULT now() |

Аккаунт создаётся самостоятельной регистрацией (ACC-1) или ИТ-администратором системы (ACC-2).
Таблицы приглашений нет — по требованию STF-1.

### 5.2. `studios`

`id uuid PK`, `name text NOT NULL`, `timezone text NOT NULL DEFAULT 'Europe/Moscow'`,
`contacts jsonb`, `referral_code text NOT NULL`, `archived_at timestamptz NULL`,
`created_at timestamptz NOT NULL DEFAULT now()`.

`referral_code` — публичный код студии (REF-1): 8 символов base32 (`a-z0-9`), генерируется при
создании студии, уникальный индекс `UNIQUE (lower(referral_code))`. Меняется владельцем или
администратором (REF-3); при смене старый код освобождается и перестаёт работать (REF-4).
Членства к коду не привязаны — смена кода не влияет на уже присоединившихся учеников.

### 5.3. `studio_working_hours`

`studio_id uuid FK`, `weekday smallint` (1–7, ISO), `opens_at time`, `closes_at time`,
`is_closed bool NOT NULL DEFAULT false`; PK `(studio_id, weekday)`;
CHECK `is_closed OR closes_at > opens_at`.

### 5.4. `memberships`

`id uuid PK`, `studio_id uuid FK`, `user_id uuid FK`, `status text` (`active` | `disabled`),
`created_at`; UNIQUE `(studio_id, user_id)`; UNIQUE `(studio_id, id)` — цель составных внешних ключей;
индекс `(user_id)`.

### 5.5. `membership_roles`

`membership_id uuid FK`, `studio_id uuid FK` (денормализация для ограничений),
`role text` CHECK IN (`owner`, `admin`, `curator`, `teacher`, `assistant`, `student`);
PK `(membership_id, role)`; **частичный UNIQUE `(studio_id) WHERE role = 'owner'`** — гарантия
ровно одного владельца (STF-5, STF-7).

### 5.6. `rooms`

`id uuid PK`, `studio_id`, `name text NOT NULL`, `capacity int NOT NULL CHECK (capacity > 0)`,
`description text`, `archived_at timestamptz`, `created_at`;
UNIQUE `(studio_id, lower(name))` — ROM-2; индекс `(studio_id)`.

### 5.7. `courses`

`id uuid PK`, `studio_id`, `name text NOT NULL CHECK (char_length(name) BETWEEN 2 AND 140)` (CLS-2),
`direction text`, `level text` CHECK IN (`beginner`, `intermediate`, `advanced`, `none`) (CLS-3),
`kind text` CHECK IN (`group`, `individual`), `default_duration_min int` CHECK IN (45, 60, 75, 90, 120) (CLS-5),
`capacity int CHECK (capacity > 0)`, `archived_at timestamptz`, `created_at`;
UNIQUE `(studio_id, lower(name))`; UNIQUE `(studio_id, id)`.

**`teacher_membership_id uuid NULL`** — преподаватель по умолчанию (CLS-7), миграция 006:

- внешний ключ `(studio_id, teacher_membership_id) → memberships (studio_id, id)`,
  `ON DELETE SET NULL (teacher_membership_id)`;
- `NULL` — преподавателя по умолчанию нет; это валидное состояние;
- составной ключ гарантирует только принадлежность той же студии (STU-4). Правило «членство активно
  и имеет роль `teacher`» БД не выражает (роль лежит в `membership_roles`) — проверяется сервисом,
  ошибка `422 NOT_A_TEACHER`;
- индекс по `teacher_membership_id` не создаётся: курсов в студии десятки, проверка FK при удалении
  членства — seq scan, приемлемо (пересмотреть при росте каталога).

### 5.8. `class_series` — правило повторения

`id uuid PK`, `studio_id`, `course_id`, `room_id`, `teacher_membership_id uuid FK → memberships`,
`weekdays smallint[] NOT NULL` (каждое 1–7), `start_time time NOT NULL`, `duration_min int NOT NULL`,
`starts_on date NOT NULL`, `until date NOT NULL`, `created_at timestamptz`.
CHECK `until >= starts_on`; CHECK `array_length(weekdays,1) > 0`.

`duration_min` — **снимок `courses.default_duration_min` на момент создания серии**, клиентом
не передаётся (SCH-2, CLS-8). Он же длительность всех материализованных сеансов серии.

Материализация: при создании серии в той же транзакции генерируются `class_sessions` на все
даты от `starts_on` до `until` по указанным дням недели. Горизонт ограничен
`until <= starts_on + interval '52 weeks'` — защита от случайной серии на десятилетие.

### 5.9. `class_sessions` — сеанс расписания

`id uuid PK`, `studio_id`, `series_id uuid NULL FK → class_series`, `course_id`, `room_id`,
`teacher_membership_id`, `starts_at timestamptz NOT NULL`, `ends_at timestamptz NOT NULL`,
`status text NOT NULL DEFAULT 'scheduled'` CHECK IN (`scheduled`, `cancelled`), `created_at`.
CHECK `ends_at > starts_at`.

Отдельной колонки длительности нет: она равна `ends_at − starts_at` и фиксируется при создании
из `courses.default_duration_min`. Последующее изменение курса сеанс не переписывает (CLS-8, SCH-10).

Ограничения пересечений (ROM-5, SCH-3) — на уровне БД, чтобы гонка двух запросов не создала конфликт:

```sql
ALTER TABLE class_sessions ADD CONSTRAINT no_room_overlap
  EXCLUDE USING gist (room_id WITH =, tstzrange(starts_at, ends_at) WITH &&)
  WHERE (status = 'scheduled');

ALTER TABLE class_sessions ADD CONSTRAINT no_teacher_overlap
  EXCLUDE USING gist (teacher_membership_id WITH =, tstzrange(starts_at, ends_at) WITH &&)
  WHERE (status = 'scheduled');
```

Индексы: `(studio_id, starts_at)`, `(studio_id, room_id, starts_at)`, `(studio_id, teacher_membership_id, starts_at)`.

Инвариант, проверяемый в сервисе: `teacher_membership_id` принадлежит этой студии, членство активно
и имеет роль `teacher` среди `membership_roles`. Внешним ключом не выражается — покрывается тестом.

### 5.10. Миграция 006 — преподаватель по умолчанию у курса

Согласована пользователем 2026-11-22 (`HANDOFF.md` §4). Файл: `migrations/006_course_teacher.sql`.

```sql
ALTER TABLE courses
  ADD COLUMN teacher_membership_id uuid;

ALTER TABLE courses
  ADD CONSTRAINT courses_teacher_membership_fk
    FOREIGN KEY (studio_id, teacher_membership_id)
    REFERENCES memberships (studio_id, id)
    ON DELETE SET NULL (teacher_membership_id);
```

- Синтаксис `ON DELETE SET NULL (column)` требует PostgreSQL 15+; в проекте PostgreSQL 18.
  Список колонок обязателен: без него PostgreSQL попытается обнулить и `studio_id`, а он `NOT NULL`.
- Бэкфилл не нужен: у существующих курсов поле остаётся `NULL`.
- Откат: `ALTER TABLE courses DROP CONSTRAINT courses_teacher_membership_fk; ALTER TABLE courses DROP COLUMN teacher_membership_id;`
- Проверки миграции: повторное применение — «нечего применять»; удаление членства-преподавателя
  обнуляет ссылку в курсе; вставка `teacher_membership_id` из другой студии — ошибка внешнего ключа.

### 5.11. Что сознательно не создаётся

- `invitations` — приглашений нет (STF-1).
- `attendance`, `subscriptions`, `student_profiles` — следующая фаза.
- Таблица «прав» — матрица 4.1 статична и живёт в коде (`rbac`), а не в БД.
- Копия длительности в `class_sessions` — избыточна, длительность выводится из `ends_at − starts_at`.
- Индекс `courses(teacher_membership_id)` — см. §5.7.

## 6. Ключевые сценарии

**Создание студии (STU-1).** Одна транзакция: `users` уже существует → `studios` →
`studio_working_hours` (7 строк) → `memberships` → `membership_roles(role='owner')`.
Ответ 201 только после коммита.

**Добавление участника (STF-1, STF-9).** Поиск `users` по `lower(email)`; нет — 404 `USER_NOT_FOUND`
(STF-2); есть — `memberships` + набор ролей (STF-4); дубль — 409 `ALREADY_MEMBER` (STF-3).
Письма не отправляются. Для роли `student` при отсутствии аккаунта он создаётся вместе с членством
в одной транзакции, а временный пароль возвращается в ответе один раз (`temporaryPassword`, STF-9);
SMTP в Фазе 1 нет, пароль передаётся ученику лично.

**Создание сеанса и серии (SCH-1, SCH-2, CLS-8).** Тело запроса не содержит `durationMin`
(передача → `422 VALIDATION`). Сервис читает `courses.default_duration_min` и
`courses.teacher_membership_id`. Если `teacherMembershipId` не передан — берётся преподаватель
курса (CLS-7); если его нет и там — `422 VALIDATION`. Явно переданный преподаватель главнее
преподавателя курса. `ends_at = starts_at + default_duration_min`. Длительность серии
фиксируется в `class_series.duration_min`. Валидация: курс и зал активны, преподаватель — активный
участник с ролью `teacher`, время в рабочих часах студии (SCH-5), `until` в пределах горизонта.
Генерация дат и `INSERT` сеансов одной транзакцией. Нарушение exclusion-ограничения
(SQLSTATE `23P01`) → откат, поиск конфликтующего сеанса → 409 с его идентификатором и временем
(SCH-3, ROM-5).

**Изменение курса (CLS-8).** `PATCH /courses/{id}` меняет `default_duration_min` и/или
`teacher_membership_id`. Существующие `class_sessions` не обновляются: их `starts_at`/`ends_at`
уже зафиксированы. Сеансы, созданные после, берут новую длительность; новые серии — новый снимок.
Изменение преподавателя курса так же не переписывает уже созданные сеансы — оно влияет только
на новые.

**Правка сеанса (SCH-10).** `PATCH /sessions/{id}` меняет зал, преподавателя и/или начало.
`durationMin` запрещён (422). При переносе `ends_at = новое начало + собственная длительность
сеанса` (разница `ends_at − starts_at` до правки), а не текущая длительность курса: прошлые
сеансы сохраняют свою длительность (CLS-8).

**Передача владения (STF-5).** Транзакция: снять `owner` у текущего, назначить новому.
Частичный уникальный индекс запрещает второго владельца, а снятие последнего владельца
отклоняет сервис (`409 LAST_OWNER`): состояния «два владельца» и «ноль владельцев» недостижимы.

**Архивация зала/курса (ROM-3, CLS-4).** `archived_at` вместо удаления; архивные не попадают
в выборку для новых сеансов, существующие сеансы сохраняются. Удаление зала запрещено при наличии
сеансов (ROM-4).

**Регистрация владельца (REF-8).** Отдельный адрес регистрации: аккаунт создаётся запросом
регистрации, затем `POST /studios` в одной транзакции создаёт студию, рабочие часы, членство и
владельца (STU-1). Реферальный код генерируется в этой же транзакции; коллизия кода — повторная
попытка (до 5), затем 500.

**Присоединение по реферальной ссылке (REF-1…REF-7).** Публичный маршрут без JWT:
`GET /join/{code}` находит студию по `lower(referral_code)`; нет — 404. Регистрация
`POST /join/{code}/register` создаёт `users` + `memberships` + `membership_roles('student')`
одной транзакцией и выдаёт JWT. Авторизованный пользователь — `POST /join/{code}/join`:
создаёт только членство; повторное обращение — 409 `ALREADY_MEMBER`. Роли сотрудника по ссылке
не выдаются никогда (REF-7): роль всегда `student`.

## 7. Время и часовые пояса

- Все моменты времени — `timestamptz`, хранение в UTC (NFR-3).
- `studios.timezone` — единственный источник локального времени студии.
- Рабочие часы и `class_series.start_time` — локальное время студии.
- Материализация серии в `timestamptz` выполняется в часовом поясе студии
  (`(starts_on + start_time) AT TIME ZONE studios.timezone`), поэтому переход на летнее время
  не сдвигает сеансы.
- Клиент отображает время в поясе студии, а не браузера.

## 8. Авторизация и права

JWT: `sub` (user id), `iat`, `exp` (24 ч). Студия в токен не зашивается — она берётся из пути и
проверяется по `memberships` (не зависит от ответа на Q3).

Без JWT доступны: `GET /health`, `POST /auth/register`, `POST /auth/login`, `GET /join/{code}`,
`POST /join/{code}/register`. Остальные маршруты требуют токен.

Каждый запрос `/api/v1/studios/{studioId}/**` проходит `tenant-guard`: активное членство → набор
ролей; иначе 403 `NOT_A_MEMBER`. Затем `rbac` проверяет действие:

| Действие | Роли |
|---|---|
| `studio.read` | любая роль |
| `studio.write` | owner, admin |
| `studio.archive` | owner |
| `members.read` | owner, admin |
| `members.write` (сотрудники) | owner, admin |
| `students.write` | owner, admin, curator |
| `rooms.write` | owner, admin, curator |
| `courses.write` | owner, admin, curator |
| `schedule.read` | любая роль |
| `schedule.write` | owner, admin, curator |

Права объединяются: участник с ролями `teacher` + `curator` получает `schedule.write` (ROL-2).
Ограничение одной роли не отменяет право, выданное другой.

**Уточнение 1.1.0.** До v1.1.0 `members.read` включал `curator`. Это противоречило ROL-7
(«персонал и настройки студии недоступны» куратору) и строке «Персонал и роли» матрицы 4.1,
где куратора нет. Право сужено до owner/admin. Потребности расписания и работы с учениками
закрываются отдельно:

- `GET /studios/{id}/teachers` — справочник преподавателей (`membershipId`, `displayName`),
  право `schedule.read`: нужен фильтру расписания и форме сеанса всем ролям; email не отдаётся;
- `GET /studios/{id}/members?role=student` — список учеников, право `students.write`:
  куратор ведёт учеников, но не видит персонал.

Права владельца и передача владения остаются прежними: набор ролей владельца правит только
владелец (ROL-6), смена владельца — только `POST /owner-transfer`. Добавляется правило ACC-9:
себе роли не назначаются — `PATCH` собственного членства возвращает 403, роли выдаёт другой
владелец или администратор.

## 9. Изоляция tenant

- `studioId` присутствует в пути каждого студийного эндпоинта и обязателен в репозиториях —
  запрос без него невозможен по типу.
- Составные внешние ключи исключают межстудийные связи, в том числе для
  `courses.teacher_membership_id` (миграция 006).
- RLS в Фазе 1 не включается: изоляция держится на уровне доступа к данным плюс тест NFR-1.
  Включение RLS — отдельное решение, не для текущей фазы.

## 10. Ошибки

Единый конверт `{ "error": { "code", "message", "details" } }`; коды в `doc/contracts.md` §9.
422 — валидация, 409 — конфликт (уникальность, пересечение, занятый зал), 403 — нет права,
404 — объект не найден или принадлежит другой студии (не раскрываем существование).
Передача запрещённого поля (`durationMin` в планировании) — 422 `VALIDATION` с
`details.fields.durationMin`, а не молчаливое игнорирование.

## 13. Риски и отложенные решения

1. **`btree_gist`** — расширение PostgreSQL, нужное для exclusion-ограничений. Если недоступно,
   конфликты проверяются в транзакции с `SELECT … FOR UPDATE` (медленнее, риск гонки выше).
2. **Материализация серий** ограничена горизонтом 52 недели и объёмом строк. Продление серии —
   отдельная задача, вне Фазы 1. Продление обязано сохранить `duration_min` существующей серии:
   иначе прошлые и будущие сеансы получат разную длительность вопреки CLS-8.
3. **Нет refresh-токенов**: сессия 24 часа, повторный вход по паролю. Пересмотр — при появлении
   требования о долгоживущей сессии (это A6.1, следующая фаза).
4. **Нет аудита изменений** (кто и когда менял роли): не входит в Фазу 1.
5. **Удаление серии** затрагивает только будущие сеансы, прошедшие остаются (SCH-8); история
   посещаемости появится с модулем A2.
6. **Перебор реферальных кодов.** Публичный `GET /join/{code}` позволяет перебирать коды: нужен
   rate limit по IP (в Фазе 1 — простой счётчик на инстансе), а код из 8 символов base32
   (≈ 40 бит) делает перебор невыгодным.
7. **Преподаватель по умолчанию — сервисный инвариант.** БД гарантирует только принадлежность
   студии. Участник может потерять роль `teacher` или быть исключён: тогда курс сохраняет
   «битого» преподавателя до `ON DELETE SET NULL` (при удалении членства) или до первой попытки
   создать сеанс, которая вернёт `422 NOT_A_TEACHER`. Отдельной проверки при смене ролей нет —
   осознанно, чтобы не блокировать снятие роли.
8. **Удаление члена с сеансами.** `class_sessions` и `class_series` ссылаются на членство без
   каскада: удаление преподавателя с сеансами отклоняется БД (SQLSTATE `23503`). Сейчас это
   необработанная ошибка 500 — существовавшее ограничение, не связанное с v0.4.0; задача на
   маппинг в 409 `MEMBER_IN_USE` — вне текущего объёма.
9. **Индекс `courses(teacher_membership_id)` не создаётся** (см. §5.7): при удалении членства
   PostgreSQL сканирует `courses`. Приемлемо для десятков курсов; при росте каталога — добавить.
10. **`ON DELETE SET NULL (column)`** требует PostgreSQL 15+; проект на 18. При откате на старую
    версию миграция не применится — это осознанно, другой способ (триггер) не вводим.

## 14. Видимость интерфейса по правам (ROL-11, ROL-12)

Спецификация для TechLead и Coder: что именно скрывается. Правило одно: элемент, на который
у роли нет права, **отсутствует в разметке**; `disabled`, `hidden`, `opacity` и проверка только
на клиенте не считаются выполнением ROL-11. Права по-прежнему проверяются на API (ROL-4),
скрытие — только UX, вторая линия защиты.

### 14.3. Источники данных для экранов

- `ScheduleTab` загружает преподавателей из `GET /studios/{id}/teachers`, а не из
  `GET /members?role=teacher`: у куратора больше нет `members.read`, но форма сеанса и фильтр
  должны работать.
- `StaffTab` использует `GET /members` (`members.read`), `StudentsTab` — `GET /members?role=student`
  (`students.write`).
- Недоступный экран не должен выполнять запросы своих данных: иначе 403 в консоли и утечка
  структуры API.

### 14.4. Решение по разделу «Команда» и ученикам

Матрица 4.1 разделяет «Персонал и роли» (owner, admin) и «Ученики студии» (owner, admin, curator),
ROL-7 прямо запрещает куратору доступ к персоналу. Поэтому:

- «Команда» — только owner/admin;
- «Ученики» — отдельная вкладка для owner/admin/curator.

Альтернатива «одна вкладка с фильтром по ученикам для куратора» отклонена: она либо показывает
куратору персонал, либо требует скрывать внутри одной вкладки разные списки, что противоречит
ROL-12 («раздел без доступных действий не отображается»). Решение подлежит подтверждению
пользователем при приёмке UI: если куратору нужен доступ к списку персонала, это меняет
`members.read` обратно и отменяет вкладку «Ученики».
