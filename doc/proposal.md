# Proposal: StudioFlow (CRM для танцевальной студии, SaaS)

> Last reviewed: 2026-11-22
> Статус: черновик, границы MVP уточняются

## 1. Vision

SaaS-платформа для управления танцевальными студиями: ученики видят свой прогресс и расписание в личном кабинете, преподаватели отмечают посещаемость и достижения, администратор управляет группами и абонементами. В перспективе — программа лояльности.

Целевой пользователь: небольшая студия (1–3 преподавателя, 30–150 учеников), у которой сейчас всё ведётся в мессенджерах и таблицах.

## 2. Problem

- Ученик не видит свой прогресс и не помнит, что было на прошлых занятиях.
- Администратор вручную напоминает о занятиях и собирает оплату.
- Нет единого места, где хранится история посещений и достижений.
- При переходе на SaaS (несколько студий) нужна изоляция данных между студиями.

## 3. Scope: In (MVP, текущий срез)

- Регистрация студии (tenant) и администратора.
- Личный кабинет ученика: расписание, история посещений, заметки преподавателя о прогрессе.
- Кабинет преподавателя: отметка посещаемости, добавление заметки о прогрессе.
- Кабинет администратора: управление группами, учениками, расписанием.
- Аутентификация: email + пароль, JWT.

## 4. Scope: Out (No-Gos для MVP)

- НЕТ программы лояльности (бонусы, скидки, уровни) — только в Known Unknowns.
- НЕТ онлайн-оплаты и интеграции с платёжными системами.
- НЕТ мобильного приложения (только адаптивный веб).
- НЕТ чата и push-уведомлений (только email-приглашения).
- НЕТ мультиязычности.
- НЕТ публичного API для интеграций.

## 5. Known Unknowns (не решено, не проектировать без подтверждения)

- **Multi-tenancy:** одна инсталляция = одна студия, или одна инсталляция обслуживает несколько студий? Влияет на схему БД и авторизацию.
- **Программа лояльности:** какие механики (баллы за посещения, скидки, уровни)? Нужна ли вообще в первый год?
- **Роли:** нужна ли роль «родитель» (оплачивает, видит прогресс ребёнка), или все ученики — взрослые?
- **Оплата:** когда-нибудь понадобится интеграция с эквайрингом? Если да — это влияет на модель абонементов.
- **Уведомления:** email достаточно, или нужны SMS/Telegram?
- **Экспорт данных:** нужен ли экспорт прогресса в PDF для ученика?

## 6. Confirmed Decisions

- Стек: TypeScript на клиенте и сервере. Клиент — React + Vite. Сервер — Node.js + Fastify. БД — PostgreSQL.
- Аутентификация: JWT, без OAuth на старте.
- Деплой: один инстанс, без Kubernetes.
- Данные изолированы по `studio_id` в каждой таблице (даже если multi-tenancy ещё не решена — закладываем поле, но не строим логику переключения).
- UI: Tailwind CSS, без сторонних UI-китов.

## 7. Success Criteria (MVP)

1. Администратор может создать студию, группу и добавить ученика.
2. Ученик входит в личный кабинет и видит расписание и историю посещений.
3. Преподаватель отмечает посещаемость, и ученик видит обновление без перезагрузки страницы (или после refresh — уточнить в Current Phase).
4. `pnpm typecheck`, `pnpm lint`, `pnpm test` проходят без ошибок.
5. Данные одной студии не видны пользователям другой студии (проверяется тестом).

## 8. Constraints

- Только PostgreSQL (не SQLite, не MongoDB).
- Никаких UI-библиотек кроме Tailwind CSS.
- Аутентификация только через JWT (не сессии).
- Все таблицы с пользовательскими данными содержат `studio_id`.
- Никаких деструктивных миграций БД без подтверждения.

## 9. Current Phase

**Фаза 1 (текущая):** каркас приложения + аутентификация + создание студии/группы/ученика.
Всё, что связано с прогрессом, посещаемостью и личным кабинетом ученика — следующая фаза, после подтверждения схемы БД.

## 10. Decision Gates (когда агент должен остановиться и спросить)

- Любое изменение схемы БД (новые таблицы или поля) — запросить подтверждение.
- Любая задача, затрагивающая Known Unknowns (multi-tenancy, лояльность, роли) — остановиться и вернуть вопрос пользователю.
- Добавление внешней зависимости (npm-пакет, сервис) — сначала предложить альтернативу без неё.
- Создание абстракции «на будущее» (интерфейс с одним наследником, конфиг для несуществующего сценария) — запрещено.
