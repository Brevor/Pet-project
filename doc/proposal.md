# Proposal: StudioFlow (CRM для танцевальной студии, SaaS)

> Last reviewed: 2026-11-22
> Статус: черновик, границы MVP уточняются

## 1. Vision

SaaS-платформа для управления танцевальными студиями: ученики видят свой прогресс и расписание в личном кабинете, преподаватели отмечают посещаемость и достижения, администратор управляет группами и абонементами. В перспективе — программа лояльности.

Целевой пользователь: небольшая студия (1–3 преподавателя, 30–150 учеников), у которой сейчас всё ведётся в мессенджерах и таблицах.

## 2. Problem

- Ученик не видит свой прогресс и не помнит, что было на прошлых занятиях.
- Администратор вручную напоминает о занятиях и собирает оплату.
- Нет единого места, где хранится история посещений и достижений.
- При переходе на SaaS (несколько студий) нужна изоляция данных между студиями.

## 3. Scope: In (MVP, текущий срез)

- Регистрация студии владельцем: SaaS, самостоятельная регистрация.
- Персонал студии и роли: владелец, администратор, куратор, преподаватель, ассистент, ученик;
  у сотрудника может быть несколько ролей.
- Залы: список помещений с вместимостью, доступных для тренировок.
- Каталог курсов: направление, уровень, тип, длительность, вместимость.
- Расписание: сеансы курсов по залам и преподавателям, повторяющиеся и разовые, с проверкой конфликтов.
- Онбординг после регистрации: создание студии или присоединение по реферальной ссылке.
- Реферальная ссылка студии (`/join/<код>`): уникальный код, редактируется владельцем или администратором.
- Личный кабинет ученика: расписание, история посещений, заметки преподавателя о прогрессе.
- Кабинет преподавателя: отметка посещаемости, добавление заметки о прогрессе.
- Кабинет администратора: управление группами, учениками, расписанием.
- Аутентификация: email + пароль, JWT.

## 4. Scope: Out (No-Gos для MVP)

- НЕТ программы лояльности (бонусы, скидки, уровни) — только в Known Unknowns.
- НЕТ онлайн-оплаты и интеграции с платёжными системами.
- НЕТ мобильного приложения (только адаптивный веб).
- НЕТ чата и push-уведомлений (только письма для установки пароля; приглашений пользователей нет).
- НЕТ мультиязычности.
- НЕТ публичного API для интеграций.

## 5. Known Unknowns (не решено, не проектировать без подтверждения)

- **Программа лояльности:** какие механики (баллы за посещения, скидки, уровни)? Нужна ли вообще в первый год?
- **Роль «родитель»:** нужна ли роль «родитель» (оплачивает, видит прогресс ребёнка), или все ученики — взрослые?
- **Участие в нескольких студиях:** может ли один пользователь состоять в нескольких студиях одновременно?
- **Оплата:** когда-нибудь понадобится интеграция с эквайрингом? Если да — это влияет на модель абонементов.
- **Уведомления:** email достаточно, или нужны SMS/Telegram?
- **Экспорт данных:** нужен ли экспорт прогресса в PDF для ученика?

Решено 2026-11-22 (см. §6): multi-tenancy — SaaS с самостоятельной регистрацией владельца;
набор ролей — шесть (владелец, администратор, куратор, преподаватель, ассистент, ученик),
у сотрудника может быть несколько ролей.

## 6. Confirmed Decisions

- Стек: TypeScript на клиенте и сервере. Клиент — React + Vite. Сервер — Node.js + Fastify. БД — PostgreSQL.
- Аутентификация: JWT, без OAuth на старте.
- Деплой: один инстанс, без Kubernetes.
- Данные изолированы по `studio_id` в каждой таблице.
- Multi-tenancy: SaaS, одна инсталляция обслуживает несколько студий; владелец регистрируется сам.
- Роли: владелец, администратор, куратор, преподаватель, ассистент, ученик; у сотрудника может быть
  несколько ролей, права складываются.
- Учётные записи: самостоятельная регистрация или создание ИТ-администратором системы (БД/API).
  Приглашений пользователей нет; письмо используется только для установки пароля.
- Присоединение учеников: по реферальной ссылке студии (`/join/<код>`); код уникален и
  редактируется владельцем или администратором. Регистрация владельца и создание студии —
  по отдельному общему адресу, без реферального кода.
- UI: Tailwind CSS, без сторонних UI-китов.

## 7. Success Criteria (MVP)

1. Владелец регистрирует студию, добавляет сотрудника с ролью и ученика.
2. Ученик входит в личный кабинет и видит расписание и историю посещений.
3. Преподаватель отмечает посещаемость, и ученик видит обновление без перезагрузки страницы (или после refresh — уточнить в Current Phase).
4. `pnpm typecheck`, `pnpm lint`, `pnpm test` проходят без ошибок.
5. Данные одной студии не видны пользователям другой студии (проверяется тестом).

## 8. Constraints

- Только PostgreSQL (не SQLite, не MongoDB).
- Никаких UI-библиотек кроме Tailwind CSS.
- Аутентификация только через JWT (не сессии).
- Все таблицы с данными студии содержат `studio_id`; глобальный аккаунт пользователя — исключение.
- Никаких деструктивных миграций БД без подтверждения.

## 9. Current Phase

**Фаза 1 (текущая, расширена 2026-11-22):** каркас приложения, аутентификация, создание студии,
персонал и роли, залы, каталог курсов, расписание сеансов.
Всё, что связано с прогрессом, посещаемостью и личным кабинетом ученика — следующая фаза, после подтверждения схемы БД.

## 10. Decision Gates (когда агент должен остановиться и спросить)

- Любое изменение схемы БД (новые таблицы или поля) — запросить подтверждение.
- Любая задача, затрагивающая Known Unknowns (лояльность, роль «родитель», участие в нескольких студиях) — остановиться и вернуть вопрос пользователю.
- Добавление внешней зависимости (npm-пакет, сервис) — сначала предложить альтернативу без неё.
- Создание абстракции «на будущее» (интерфейс с одним наследником, конфиг для несуществующего сценария) — запрещено.

## 11. Журнал решений (2026-11-22)

По запросу на модуль «ядро студии» (`doc/requirements/studio.md`, `approved` v0.3.1) уточнены границы:

- **Q1 → закрыто.** SaaS: одна инсталляция обслуживает несколько студий, владелец регистрируется сам.
  Внесено в §6.
- **Q2 → закрыто.** Шесть ролей; у сотрудника может быть несколько ролей; матрица прав 4.1 подтверждена.
  Внесено в §6.
- **Q4 → закрыто.** «Список занятий» — каталог курсов; расписание состоит из сеансов курсов.
- **Q5 → закрыто.** Фаза 1 расширена: студия, персонал и роли, залы, каталог курсов, расписание.
  Внесено в §3 и §9.
- **Q6 → закрыто.** Ученик добавляется администратором (в том числе с созданием аккаунта) либо
  регистрируется самостоятельно.
- **Q7 → закрыто.** Присоединение учеников — по реферальной ссылке студии; регистрация владельца
  и создание студии — по общему адресу. Внесено в §6 и studio.md §3.1.
- **Открыто:** Q3 (участие в нескольких студиях), Q8 (роль «родитель», §5).

Детали требований и приёмки — в `doc/requirements/studio.md`.
